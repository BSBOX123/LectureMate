# Step 23: 전사 청킹 (검색 단위 재설계)

- 기간: 2026-09-29
- 커밋: (검토 후 커밋 예정)
- 배경: "벡터 DB 저장 형식이 이미 정형화돼 있나, 아니면 설계에 따라 성능이 달라지나?" 라는 질문에
  답하려고 실제 데이터를 재 보다가 **설계 결함**을 발견했다.

## 발견: 검색 단위가 잘게 부서져 있었다

과목 17의 청크 크기 분포다.

| | 개수 | 평균 글자 | 최소 | 최대 |
|---|---|---|---|---|
| 자료 페이지 | 209 | 310 | 13 | 999 |
| **녹음 세그먼트** | **1,373** | **21** | **1** | 747 |

녹음 쪽 길이 분포를 더 보면:

| 길이 | 개수 | 비율 |
|---|---|---|
| **10자 미만** | **501** | **36.5%** |
| 10~19자 | 285 | 20.8% |
| 20~39자 | 421 | 30.7% |
| 40자 이상 | 166 | 12.1% |

실제로 저장된 것들이다.

```
30초  "박준오"
34초  "박준오"
36초  "유호찬"
39초  "이다은"      ← 출석 부르는 소리가 각각 한 행 + 1024차원 벡터 하나씩
```

**Whisper 가 끊어 준 단위를 그대로 한 행으로 만든 설계 탓이다.** 20자 조각에는 임베딩할 의미가
거의 없다. Step 22 에서 "교수님이 강조한 부분" 질문에 "수요일 강의가 인정이 됩니다" 같은 무관한
조각이 걸렸던 것도 절반은 이 때문이었다. **검색이 나쁜 게 아니라 검색 대상이 부서져 있었다.**

## 설계: 원본을 남기고 검색용 덩어리를 따로 둔다

```
recording_segments   Whisper 원본 그대로. 임베딩 없음.  → 요약(정밀 타임스탬프), 재청킹의 원본
recording_chunks     이웃을 약 300자로 묶음 + 임베딩    → 검색
```

**원본을 덮어쓰지 않은 이유:** 전사에 71분 녹음 기준 42분이 든다. 파라미터를 바꿔 다시 묶고
싶을 때 원본이 없으면 전사를 다시 돌려야 한다. 요약도 정밀한 타임스탬프를 쓴다.

목표 크기는 **300자** — 자료 페이지 평균(310자)에 맞췄다. 실측 비교:

| 목표 | 덩어리 수 | 평균 | 최소 |
|---|---|---|---|
| 200자 | 117 | 239 | 199 |
| **300자** | **72** | **346** | **299** |
| 400자 | 52 | 442 | 399 |

**겹침(overlap) 60자**를 둬 개념이 경계에 걸려 잘리는 것을 줄였다. 덩어리끼리 시간이 겹친다
(40:58~42:04, 41:37~42:52).

세그먼트의 임베딩 컬럼과 HNSW 인덱스는 지웠다 (쓰이지 않는데 5.6MB + 8.8MB 를 차지했다).

## 결과

| | 전 | 후 |
|---|---|---|
| 검색 단위 | 세그먼트 1,992개, 평균 21자 | **덩어리 197개, 평균 342자** |

"GROUP BY 를 쓸 때 주의할 점이 뭐야?" 의 검색 결과다.

```
[9월 28일 수업 45:19] 그룹바의 속성과 집계함수. 두 가지만 쓸 수가 있다. 다른 속성은 select 를 사용할 수 없다
[9월 28일 수업 51:35] 그룹에 대한 조건은 웨어(WHERE)가 아니라 ... 헤빙(HAVING)입니다
[9월 28일 수업 44:41] 학번을 찍으라고 했죠? ... 이게 될까 안될까?
```

Step 22 요약이 "강조했다" 고 짚은 바로 그 내용들이다. 전에는 같은 질문에 9~53자짜리 조각이
걸렸다.

**"강조하신 부분" 질문은 여전히 안 된다.** 예상대로다 — 그건 청킹으로 풀리는 문제가 아니라
집계 질문이고, Step 22 의 요약 기능이 맡는다.

## 백필

기존 전사를 다시 돌리지 않고 DB 의 세그먼트를 묶어 임베딩만 새로 만들었다
(`ai-engine/scripts/backfill_chunks.py`). 녹음 3개, 1,992 세그먼트 → 197 덩어리.

## 트러블슈팅: 테스트 DB 에 마이그레이션을 수동 적용하면 안 된다

pytest 를 먼저 돌리려고 `lecturemate_test` 에 V7 을 `psql` 로 직접 넣었더니, 나중에 Spring Boot
테스트에서 **Flyway 가 46개 전부 실패**했다. 객체는 이미 있는데 Flyway 기록에는 없어서다.

```
Caused by: org.flywaydb.core.internal.exception.FlywayMigrateException
```

테스트 DB 를 지우고 다시 만들어 Flyway 가 V1~V7 을 정상 경로로 적용하게 했다. CI 는 마이그레이션
파일을 직접 적용하므로(Spring 없이 FastAPI 테스트를 돌려야 한다) 문제가 없지만, **로컬에서는
순서를 지켜야 한다** — 스키마가 바뀌면 Spring 테스트를 먼저 돌려 Flyway 가 적용하게 하고,
그다음 pytest 를 돌린다.

## 검증

FastAPI 42개(신규 8: 청킹 단위 테스트), Spring Boot 46개, web-client 11개 통과.

## 남은 일

- 자료 페이지도 쪽 단위(평균 310자, 최대 999자)다. 큰 쪽은 더 쪼갤 여지가 있다
- 임베딩에 맥락을 붙이지 않는다 (지금은 본문만). "[데이터베이스 3장 19쪽]" 처럼 앞에 붙이면
  자료 이름으로 거르는 질문에 더 잘 걸릴 수 있다
- 청킹 파라미터(300자/60자)를 검색 품질로 평가할 수단이 없다
