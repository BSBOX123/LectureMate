# Step 18: 실제 강의 사용 후 개선 (자막 토글 · 전사 속도 · 분석 안내)

- 기간: 2026-09-21
- 커밋: (검토 후 커밋 예정)
- 배경: 실제 수업(데이터베이스 3장, 128쪽 PDF + 36분 녹음)에서 처음 써 본 뒤 나온 문제 3가지

## 사용자가 겪은 문제

1. **실시간 자막이 엉망** — 내용을 알아볼 수 없는 수준
2. **발열이 심함** — 녹음 내내 노트북이 뜨거워짐
3. **분석하는 방법을 모르겠음** — 녹음 후 무엇을 눌러야 하는지, 진행 중인지 알 수 없음

## 먼저 측정한 것

실제 녹음(`19.wav`)의 같은 1분 구간을 세 방식으로 전사해 비교했습니다.

| 방식 | 결과 | 처리 시간 |
|---|---|---|
| 실시간 자막 (base, 3초 청크) | "요사씨가 표정해야 되는 뇨골에... 엄청 잘생겼어요" — 내용 파악 불가 | 60초 음성에 **40초** |
| base, 1분 통째로 | "3시간을 표정해야 되는데... DV들은 못 샀다" — 여전히 나쁘지만 문맥은 남음 | 14초 |
| **large-v3** | "**테이블 릴레이션**이 있고 **데이터 값은 특정 레코드의 특정 컬럼의 값**... **도메인은 각각 컬럼에 속하는 데이터**" | 208초 |

**결론:** 자막이 나쁜 원인은 두 가지가 겹친 것입니다.
- 모델 크기: base 는 한국어 전문 용어에 약함
- 3초 청크: 문장 중간을 잘라 문맥이 없음 (같은 base 라도 통째로 들으면 훨씬 나음)

**중요:** 저장된 녹음으로 하는 정밀 전사는 품질이 전혀 다릅니다. 실시간 자막을 꺼도 최종 결과에는 영향이 없습니다.

발열도 측정으로 설명됩니다. 실시간 자막은 **60초 음성을 처리하는 데 40초**를 씁니다. 녹음 내내 CPU 의 3분의 2를 계속 점유합니다.

## 1. 실시간 자막을 끌 수 있게 (기본 꺼짐)

- `WS /ws/v1/lectures/{id}/audio?token=...&preview={true|false}` — SPEC §2.1-2 에 추가
- `preview=false`(기본)면 Spring Boot 가 FastAPI 에 연결하지 않고 PCM 을 파일에만 쌓습니다
- 화면에는 "실시간 자막" 체크박스(기본 해제, 녹음 중에는 변경 불가)를 두고, 설명을 툴팁으로 달았습니다

**이렇게 한 이유:** 자막 품질이 낮아 효용이 적은데 발열 비용은 큽니다. 끄면 Whisper 가 아예 돌지 않습니다. 녹음 저장과 정밀 분석은 그대로입니다.

## 2. 전사 속도: mlx-whisper (Apple GPU)

`faster-whisper`(CTranslate2)는 Metal 을 지원하지 않아 Mac 에서 CPU 로만 돕니다. Apple MLX 기반 `mlx-whisper` 를 백엔드로 추가했습니다.

| 백엔드 | 1분 음성 처리 | 36분 강의 환산 |
|---|---|---|
| faster-whisper (CPU) | 208초 | 약 127분 |
| **mlx-whisper large-v3 (GPU)** | **16초** | **약 10분** |
| mlx-whisper large-v3-turbo | (첫 실행 포함 100초) | 품질이 더 낮음 — 한국어가 영어로 튐 |

- `STT_BACKEND=mlx|faster-whisper` 로 전환합니다. 테스트와 CI(Linux)는 `faster-whisper` 로 고정합니다
- `requirements.txt` 에는 환경 마커를 달아 **Apple Silicon 에서만 설치**되게 했습니다

### 반복 루프 문제 (중요)

36분 파일을 통째로 넘겼더니 **4시간 30분이 지나도 끝나지 않았습니다.** Whisper 가 같은 구절을 무한 반복하는 상태에 빠진 것으로 보입니다. 두 가지로 막았습니다.

1. `condition_on_previous_text=False` — 앞 구간 텍스트를 다음 구간 디코딩에 물리지 않습니다
2. **5분 단위로 나눠 처리** — 한 구간이 망가져도 전체가 멈추지 않고, 진행 로그도 남습니다

5분 구간 측정: 119초 (36분 환산 약 15분).

**실제 36분 강의 전사 결과 (수정 후):**

```
894초 (14.9분), 세그먼트 436개

[0:00] 오늘 이제 SQL을 하는데
[17:23] dp랑 외의 키나 주키 이름이 똑같은 거야
[17:27] 각 개 줄 수도 있고 외의 키 이름을 주키와 다르게 줄 수도 있고
[17:32] 그것들마다 SQL이 조금씩 달라져야 하는 걸 표시하기 위해서
[36:28] 감사합니다.
```

수정 전에는 같은 파일이 **4시간 30분이 지나도 끝나지 않았습니다.** 처음부터 끝까지(0:00 ~ 36:28) 타임스탬프가 정상적으로 붙었습니다.

품질은 완벽하지 않습니다("외래 키" → "외의 키", "기본 키" → "주키"). 다만 문장 구조와 흐름은 살아 있어 슬라이드 정렬과 필기 생성에는 쓸 만합니다.

## 3. 분석 흐름 안내

대시보드 상단에 상태별 배너를 추가했습니다.

| 상태 | 표시 |
|---|---|
| 녹음은 있는데 분석 전 | **"녹음이 저장되었습니다. 정밀 분석을 시작하면 교수님 말씀을 글로 옮기고 슬라이드별 필기를 만듭니다. 36분 강의 기준 약 10분 걸립니다."** + 큰 버튼 |
| 분석 중 | "음성을 글로 옮기는 중입니다" → 전사가 끝나면 "슬라이드별 필기를 만드는 중입니다 (매칭된 슬라이드 N쪽)" + 경과 시간 + "창을 닫아도 계속 진행됩니다" |
| 실패 | "분석에 실패했습니다" + 다시 시도 버튼 |

"분석 전" 판단은 **타임라인이 비어 있는지**로 합니다(전사 결과가 없다는 뜻). 새 API 없이 기존 조회로 해결했습니다.

## 검증 결과

- Spring Boot 테스트: WebSocket 6개 포함 전체 통과. 신규 2개는 **실시간 자막을 끄면 FastAPI 없이도 녹음이 저장되는지**, **파라미터가 없으면 기본이 꺼짐인지** 확인
- FastAPI 45개, web-client 9개 통과. lint·타입 검사·빌드 통과
- **실제 36분 강의 전사: 894초(14.9분), 436개 세그먼트** — 수정 전 4.5시간 미완 → 정상 완료

## 남은 일

- 실시간 자막을 켜야 할 때를 위해 품질 개선 여지 (더 긴 청크, mlx base 사용 등)
- 분석 진행률이 "전사 중 / 필기 중" 두 단계뿐입니다. 전사 진행 비율은 서버 로그에만 남습니다
- 128쪽 강의의 자동 필기는 LLM 호출이 많아 시간과 구독 사용량이 큽니다
- 전문 용어 오인식이 남아 있습니다("외래 키" → "외의 키"). 용어 사전(initial_prompt)으로 개선할 여지가 있습니다
