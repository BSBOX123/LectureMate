# Step 22: 녹음 요약 (채팅으로 답할 수 없는 질문)

- 기간: 2026-09-28
- 커밋: (검토 후 커밋 예정)
- 배경: "9월 28일 녹음에서 교수님이 강조하신 부분 찾아줘" 가 엉뚱한 답을 냈다.

## 실패한 답변

사용자가 채팅으로 물었을 때 나온 답이다.

> 9월 28일 수업 녹음에서 확인되는 발화는 4:41의 "2025년 9월 28일 이렇게 이제 나오게 됩니다."
> 라는 한 문장뿐입니다. (...) "데이터베이스 3장" 으로 표시된 발화들이 같은 녹음인지도 알 수
> 없어서, 그 발화들은 9월 28일 강조 내용으로 묶지 않았습니다.

71분 수업에서 한 문장만 찾았다. 검색 결과를 직접 보니 이유가 분명했다.

```
질문: "녹음본 9월 28일에서 교수님이 강조하신 부분 찾아줘"

검색된 발화 5건:
  [데이터베이스 3장] 0:57  수요일 강의가 인정이 됩니다.        ← 무관
  [9월 28일 수업]   4:22  여기 레코드 하나가 있으면 좋겠다.   ← 무관
  [데이터베이스 3장] 7:35  테이프를 검색하겠다.               ← 무관
```

## 원인 두 가지

### 1. 이건 검색 질문이 아니라 집계 질문이다

**"강조한 부분" 은 주제가 아니어서 임베딩이 매칭할 대상이 없다.** 전사에 "이것은 강조한
내용입니다" 라고 적혀 있지 않다. 질문 벡터는 "9월 28일" 같은 낱말에 가까운 조각을 끌어온다.

게다가 1,373개 세그먼트에서 `top_k=5` 만 가져온다. **71분 수업을 조각 5개로 요약할 수 없다.**
RAG 의 top-k 검색으로는 구조적으로 답할 수 없는 질문이다.

### 2. 녹음 제목이 자료 제목과 겹쳤다

| | 제목 |
|---|---|
| 자료 19 | 데이터베이스 3장 |
| **녹음 19** | **데이터베이스 3장** |

V3 마이그레이션이 `lectures.title` 을 자료와 녹음 양쪽에 복사한 흔적이다. 프롬프트가 섹션으로
구분하고 있어도 **이름이 같으면 모델이 어느 쪽 것인지 판단하지 못한다.** 답변이 직접 그렇게
말했다. 녹음 19 를 `9월 21일 수업` 으로 바꿨다.

## 해결: 전사 전체를 한 번에 읽힌다

검색하지 않고 전사 전부를 LLM 에 넘긴다. 크기를 먼저 확인했다.

| 녹음 | 세그먼트 | 글자 | 예상 토큰 |
|---|---|---|---|
| 9월 21일 수업 (36분) | 438 | 11,669 | 약 5,300 |
| 9월 28일 수업 (71분) | 935 | 16,622 | 약 7,600 |

**한 번에 들어간다.** 제거했던 자동 필기(Step 12)가 무거웠던 이유는 **슬라이드마다** 호출해
128번이 됐던 것인데, **녹음 단위면 1회**다. 같은 가치를 1/128 비용으로 얻는다.

### 구현

- `V6__recording_summary.sql`: `course_recordings` 에 `summary TEXT`, `summarized_at` 추가
- `ai-engine/services/summary_service.py`: 세그먼트를 `[분:초] 텍스트` 로 이어 붙여 LLM 1회 호출
- `POST /ai/v1/recordings/{id}/summarize` → `{ "summary": "..." }` (동기, 실측 39초)
- `POST|GET /api/v1/courses/{cid}/recordings/{rid}/summary` — 만들기 / 조회
- 화면: 녹음을 누르면 **가운데 PDF 자리에 요약**이 뜬다 (읽는 문서이므로)

**동기 호출로 둔 이유:** 39초이고 `read-timeout` 이 120초다. PDF 파싱도 같은 방식이다. 전사(수십 분)
처럼 Webhook 을 쓸 이유가 없다.

**저장은 Spring 이 한다.** FastAPI 는 요약 텍스트만 돌려준다. `course_recordings` 는 Spring 소유
테이블이라는 규칙을 지킨다.

**목록에는 `hasSummary` 만 싣는다.** 요약 본문(2,334자)을 목록마다 실으면 무거워진다.

## 실제 결과

9월 28일 녹음(71분)으로 돌린 결과다. 39.4초, 2,334자.

```
교수님이 특히 강조한 부분
1. GROUP BY를 "이제 중요한 것"이라고 짚었습니다 [42:08]. 그룹을 나누는 이유는 남녀별,
   학과별 평균처럼 전체가 아니라 그룹마다 집계하려는 것입니다 [42:36].
2. GROUP BY를 쓰면 SELECT에 올 수 있는 것은 GROUP BY 속성과 집계함수 두 가지뿐입니다 [45:19].
3. 집계 결과에 대한 조건은 WHERE가 아니라 HAVING에 씁니다 [51:07, 51:35].
4. 날짜 함수는 DBMS마다 차이가 가장 큽니다 [2:33, 6:43].
5. 서브쿼리 결과가 한 행이면 =를 쓰고, 여러 행일 수 있으면 IN을 씁니다 [62:11].
```

**시각이 붙어 있어 그 대목을 찾아 들을 수 있다.** 인식이 망가진 구간은 지어내지 않고 그렇다고
적는다 ("인식이 되는 구간에서는 시험이나 과제를 직접 언급한 대목을 찾지 못했습니다").
